# Этап 6: Rust-примитивы столкновений (`collision` + `rigidBody`) ✅ выполнен

**Объём**: L · **Репозитории**: `vimp` (ядро) · **Зависит от**: этап 2

## Зачем

Предсказание контактов на клиенте (этапы 8–10) требует, чтобы клиент видел
геометрию карты так же, как хост. В `tank-battle` для этого есть два чистых
модуля без зависимостей от Pixi и Rapier — они общие для клиента и сервера.
В VIMP их нет **ни в движке, ни в плагине**: движковое ядро содержит только
`client/raycast.rs`, а `vimp-tanks/core/src/client/predictor.rs:2` прямо
объявлен «репликой модели движения **без Rapier-коллизий**».

Место — движок, а не плагин: это геометрия карты и общий решатель контактов,
а карту (`packages/engine/core/src/map.rs`) и её физику владеет движок. Любая
вторая игра с толкаемыми телами упрётся в то же самое.

## Что в tank-battle

**`src/lib/collision.js`** (220 строк):
- `boxCenterFromOrigin(x, y, angle, halfW, halfH)` — «угол объекта» (позиция
  тела Rapier для динамики карты) → центр бокса.
- `obbVsObb(a, b)` — пересечение двух ориентированных боксов по SAT.
- сбор контактов OBB с тайловой сеткой стен.
- `CONTACT_MANIFOLD_RATIO = 0.15` — ширина контактного пятна как доля габарита.
  Одиночная опорная вершина при почти плоском контакте даёт автоколебание:
  импульс перекидывает корпус через положение «заподлицо». Вершины грани
  смешиваются с непрерывным весом.

**`src/lib/rigidBody.js`** (180 строк):
- `integrate(...)` — шаг тела в порядке Rapier.
- двухтельный решатель контактов (sequential impulse) — приближение Rapier,
  не копия; остаток расхождения прячет реконсиляция.
- `MAP_SURFACE = { friction: 0.2, restitution: 0 }` — дефолты коллайдеров хоста;
  реплика обязана брать те же значения.
- `combineSurfaces(a, b)` — правило среднего (`CoefficientCombineRule::Average`).
- `boxMassProperties(...)` — масс-инерционные свойства прямоугольника.

Формат тела: `{ x, y, angle, vx, vy, angvel, invMass, invInertia,
linearDamping, angularDamping }`; статика — `invMass: 0, invInertia: 0`;
`x/y` — **центр** бокса, не «угол объекта».

Тесты: `tests/lib/collision.test.js`, `tests/lib/rigidBody.test.js` (277 строк).

## Что сейчас в движке

- `packages/engine/core/src/physics.rs` — обёртка Rapier (хостовая сторона),
  `normalize_angle`, `lerp`, `deg_to_rad`, `encode_map_object`.
- `packages/engine/core/src/client/raycast.rs` — приближённая реплика луча,
  уже перенесена (маркер «срез 2.6»).
- Ни OBB/SAT, ни решателя контактов, ни `MAP_SURFACE`, ни `boxMassProperties`.

## Шаги

1. Новый модуль `packages/engine/core/src/client/collision.rs` — порт
   `collision.js`. Сетку стен брать из уже существующего представления карты
   в клиентском ядре (сверить с `client/raycast.rs`, чтобы не завести второе
   несогласованное представление).
2. Новый модуль `packages/engine/core/src/client/rigid_body.rs` — порт
   `rigidBody.js`. Константы `MAP_SURFACE`, `DEFAULT_FRICTION`,
   `DEFAULT_RESTITUTION` **не дублировать**: свести с уже имеющимися в
   `core/src/map.rs:9-11`, они обязаны быть одним источником.
3. Экспортировать оба модуля из `client/mod.rs` так, чтобы игровое ядро
   плагина могло их использовать (`vimp_engine_core::client::...`) —
   проверить, что `vimp-engine-core` отдаёт их как публичный API крейта.
4. Обновить `packages/engine/docs` (`core.md`) и `CHANGELOG.md`; выпустить
   minor-версию крейта и пакета.

## Тесты

Портировать оба набора из `tank-battle/tests/lib/`:
- `collision.test.js` — SAT на пересекающихся/касающихся/разнесённых боксах,
  `boxCenterFromOrigin` для повёрнутого объекта, сбор контактов во внутреннем
  углу тайловой сетки.
- `rigidBody.test.js` — покой не порождает импульса, плоский контакт не
  автоколеблется (тот самый `CONTACT_MANIFOLD_RATIO`), правило среднего
  для поверхностей, инерция прямоугольника.

## Готово когда

- `cargo test --workspace` в `vimp` зелёный, оба набора перенесены.
- Крейт опубликован (или доступен по пути) для плагина.
- `packages/engine/docs/{en,ru}/core.md` описывает новые модули.

## Риски

Этап ничего не меняет в поведении игры сам по себе — это чистая инфраструктура.
Главный риск — **завести второе представление геометрии карты**, расходящееся
с тем, что видит `raycast.rs`. Проверять на совпадение результатов луча и
контакта на одной и той же стене.
