## 1. О проекте

**Tank Battle** — многопользовательская 2D-игра про танки в реальном времени.

- **Сервер**: Node.js + Express + `ws` + физика Rapier 2D (авторитетный).
- **Клиент**: PixiJS.
- **Транспорт**: WebSocket, бинарные snapshot-кадры (30 кадров/с).
- **ES-модули** (`"type": "module"`), без TypeScript.

Документация — основной источник правды об устройстве подсистем:
[docs/en/README.md](../docs/en/README.md) (первичная) и
[docs/ru/README.md](../docs/ru/README.md) (зеркало). Прочитать перед работой:

- [docs/ru/server.md](../docs/ru/server.md) — серверные модули;

## 2. Задача

### 2.1 Симптом

Танк, наезжающий на динамический элемент карты (ящик), едет некорректно:
проваливается в ящик, а через ~100 мс его выдёргивает рывком; при попытке
толкать ящик танк сносит вбок.

### 2.2 Причина

Мир на клиенте рисуется **в двух разных временах**:

| Что | В какой момент времени рисуется |
|---|---|
| свой танк | «сейчас» — client-side prediction (`TankPredictor`) |
| чужие танки, ящики, всё остальное | `serverNow − interpolation.delay`, задержка **100 мс** (`SnapshotInterpolator`) |

Пока ящик стоит, разницы нет. Как только ящик поехал (его толкают), сервер за
эти 100 мс уводит его на `скорость × 0.1` вперёд относительно нарисованного.
Сервер считает столкновение по своему, «настоящему» положению ящика, поэтому
авторитетная позиция танка совершенно законно оказывается **внутри
нарисованного** ящика. Любая попытка на клиенте «выдавить» танк из
нарисованного ящика борется с сервером, а при глубоком заходе минимальная ось
SAT становится поперечной — и танк выталкивает вбок.

### 2.3 Что уже пробовали и почему это не решение

Предыдущая итерация маскировала рассинхрон на стороне танка: проход коллизий по
нарисованным ящикам, зажим позиции рендера, приведение серверного состояния к
геометрии перед расчётом `visualError`. Это **откачено** (шаг выполнен, из плана
удалён). Маскировка не устраняет причину и добавляет собственные артефакты
(пила 30 Гц, тряска камеры, снос вбок).

### 2.4 Решение

Убрать рассинхрон: **предсказывать саму динамику карты** и рисовать её в том же
временном кадре, что и свой танк. Тогда нарисованный танк и нарисованный ящик
приходят из **одной** симуляции, и выдавливать друг из друга их нечем.

## 3. Как устроен текущий поток данных

### 3.1 Серверный тик → кадр

1. [src/server/modules/VIMP.js](../src/server/modules/VIMP.js), метод
   `_onShotTick` — берёт `SnapshotManager.processTick()` и дописывает динамику
   карты под ключом `setId` текущей карты:
   `gameSnapshot[this._roundManager.currentMapData.setId] = this._game.getDynamicMapData();`
2. [src/server/modules/Game.js](../src/server/modules/Game.js) `getDynamicMapData()`
   делегирует в [src/server/parts/Map.js](../src/server/parts/Map.js)
   `getDynamicMapData()`, который отдаёт `{ dN: [x, y, angle] }`
   (`roundTo2Decimals`).
3. [src/lib/snapshotCodec.js](../src/lib/snapshotCodec.js) `SnapshotPacker`
   пакует блоки. Тип блока определяется по `kind` из
   [src/config/opcodes.js](../src/config/opcodes.js) `SNAPSHOT_KEYS`:
   ключи `c1`/`c2` имеют `kind: 'dynamics'`.

### 3.2 Кадр → экран

1. [src/client/main.js](../src/client/main.js), `ws.onmessage`: бинарный кадр →
   `unpackFrame` → `interpolator.push(frame.snapshot, frame.camera, frame.serverTime, now)`
   и, если в кадре есть `player`-блок, `predictor.onServerState(frame.player, frame.serverTime, interpolator.offset, now)`.
2. `renderTick()` (там же) каждый rAF:
   `interpolator.sample(now)` → `{ frames, game, camera }`; `frames` (события)
   и `game` (интерполированные позиции) уходят в `applyGameData(...)`.
3. `applyGameData` разводит блоки по полотнам через `gameSets`/`entitiesOnCanvas`
   ([src/config/client.js](../src/config/client.js)) и зовёт
   `GameCtrl.parse(name, instances)`.
4. Спрайт ящика — [src/client/parts/Map.js](../src/client/parts/Map.js),
   `update(data)`:
   ```js
   this.sprite.x = data[0] / this.scale.x;
   this.sprite.y = data[1] / this.scale.y;
   this.sprite.rotation = data[2];
   ```
   То есть на вход ждёт **мировые (уже масштабированные) координаты** в
   соглашении «угол объекта» (см. 4.1).

### 3.3 Предсказание своего танка

[src/client/TankPredictor.js](../src/client/TankPredictor.js) — реплика серверной
модели движения без коллизий:

- `applyInput(action, name, localTime)` пишет изменения клавиш в историю;
- `update(localNow)` крутит аккумулятор фикс-шагом `timeStep` и зовёт `_step(keys)`;
- `onServerState(player, serverTime, offset, localNow)` — реконсиляция:
  состояние := серверное, затем **replay** истории ввода от `serverTime` кадра до
  оценки серверного «сейчас»; расхождение старого предсказания с новым уходит в
  `_visualError` и экспоненциально затухает (`ERROR_DECAY_RATE`), при большом
  расхождении — снап (`ERROR_SNAP_DISTANCE`);
- `getRenderState()` отдаёт `state + visualError`.

⚠️ Порядок интеграции в `_step` — эмпирический, повторяющий Rapier, и **закреплён
паритет-тестом** `tests/server/TankPredictorParity.test.js`: импульсы → интеграция
позиций скоростью **до** демпфирования → демпфирование `v *= 1/(1 + dt·d)`.
Этот порядок менять нельзя.

### 3.4 Геометрия динамики на клиенте

[src/client/MapDynamics.js](../src/client/MapDynamics.js) — реестр боксов
динамики карты. Сейчас его читают:

- [src/client/ShotPredictor.js](../src/client/ShotPredictor.js) — raycast
  трассера (`getBoxes`, `toLocal`);
- [src/client/parts/effects/shot/ShotEffectController.js](../src/client/parts/effects/shot/ShotEffectController.js)
  — точка появления осколков (`getBox`).

Инжектится как сервис через `componentDependencies` в
[src/config/client.js](../src/config/client.js) (`mapDynamics: ['ShotEffect']`).

⚠️ В `MapDynamics` **намеренно нет** метода сброса: `CLEAR` чистит полотно, а не
карту, и приходит в том числе на старте раунда **без** последующей `MAP_DATA`.
Сброс по `CLEAR` стирал бы боксы навсегда. Не добавлять.

### 3.5 Общие примитивы столкновений

[src/lib/collision.js](../src/lib/collision.js):

- `boxCenterFromOrigin(x, y, angle, halfW, halfH)` — «угол объекта» → центр;
- `obbVsObb(a, b)` → `{ nx, ny, depth, cx, cy } | null` — SAT двух повёрнутых
  прямоугольников; нормаль направлена **от центра `a` к центру `b`**, `cx/cy` —
  мировая точка контакта, посчитанная по вершинам `a`;
- `obbVsTileGrid(obb, grid, iterations)` → суммарное выталкивание из стен.

Константа `CONTACT_MANIFOLD_RATIO = 0.15` смешивает вершины задетой грани.
Она **необходима**: одиночная опорная вершина при контакте почти заподлицо даёт
автоколебание — импульс перекидывает корпус через положение «заподлицо»,
опорным становится противоположный угол, и так каждый шаг. Не убирать.

Сейчас `obbVsObb`/`obbVsTileGrid` в `src/` никем не используются (только
тестами) — они ждут этой работы.

## 4. Соглашения и формулы, которые обязательно знать

### 4.1 Позиция динамического тела — это УГОЛ, а не центр

В [src/server/parts/Map.js](../src/server/parts/Map.js), `createDynamic()`, тело
создаётся в `data.position`, а коллайдер смещён на полразмера:

```js
this._world.createCollider(
  RAPIER.ColliderDesc.cuboid(data.width / 2, data.height / 2)
    .setTranslation(data.width / 2, data.height / 2)   // ← смещение
    ...
```

Значит `body.translation()` — это **левый верхний угол** объекта в его
собственном повёрнутом фрейме, а не центр бокса. Именно это значение уходит в
снапшот (`c1`/`c2`) и именно его ждёт `parts/Map.js update()`.

Перевод в центр: `boxCenterFromOrigin` (`src/lib/collision.js`).
Обратный перевод (понадобится в `getRenderData`):

```js
const originFromBoxCenter = (cx, cy, angle, halfW, halfH) => {
  const offset = rotateVec({ x: halfW, y: halfH }, angle);
  return { x: cx - offset.x, y: cy - offset.y };
};
```

Этот баг («угол приняли за центр») уже ловили однажды — он сдвигал точку
попадания примерно на полгабарита ящика. Не повторять.

### 4.2 Масштаб карты

[src/server/core/RoundManager.js](../src/server/core/RoundManager.js),
`createMap()`:

```js
this._currentMapData = { scale: this._mapScale, ...this._maps[this._currentMap] };
```

Порядок спреда важен: **собственный `scale` карты перебивает глобальный**
`game.mapScale` (0.3). У `canopy` — `0.2`, у `pool_mini` — `0.6`, у `garden`
собственного нет → 0.3.

Физика сервера идёт по `_scaledMapData` (позиции и размеры умножены на `scale`),
а клиенту в `MAP_DATA` уходит **немасштабированная** `physicsDynamic` плюс поле
`scale`. Клиент обязан домножать сам — так уже делает `MapDynamics.setMap`.

### 4.3 Масс-инерционные свойства

Плотность/демпфирование приходят в `MAP_DATA` вместе с геометрией (см.
[src/data/maps/canopy.js](../src/data/maps/canopy.js)): `density`,
`linearDamping`, `angularDamping`.

```
w = item.width  * scale
h = item.height * scale
m = item.density * w * h
I = m * (w² + h²) / 12        // момент инерции прямоугольника вокруг центра
```

Танк — [src/data/models.js](../src/data/models.js), модель `m1`:
`size: 2`, габарит `width = size*4 = 8`, `height = size*3 = 6`,
`fixture.density = 200` → `m = 200 · 8 · 6 = 9600`,
`I = 9600 · (64 + 36) / 12 = 80 000`. Размер танка **не** масштабируется картой.

Ящик `canopy`: `96 · 0.2 = 19.2` по обеим сторонам, `density 20` →
`m ≈ 7373`, `I ≈ 452 985`. Массы сопоставимы — двухтельный контакт обязателен,
приближение «ящик бесконечно тяжёлый» даёт заметно неправильную картину.

### 4.4 Параметры поверхностей

| Тело | friction | restitution | источник |
|---|---|---|---|
| танк | 0.5 | 0.1 | `models.js` → `m1.fixture` |
| ящик, стена | 0.2 | 0 | `DEFAULT_FRICTION`/`DEFAULT_RESTITUTION` в `src/server/parts/Map.js` |

Rapier комбинирует коэффициенты правилом **среднего** (`CoefficientCombineRule::Average`),
поэтому в контакте:

- танк↔ящик и танк↔стена: `friction 0.35`, `restitution 0.05`;
- ящик↔ящик и ящик↔стена: `friction 0.2`, `restitution 0`.

### 4.5 Двухтельное разрешение контакта (формулы)

Даны тела `A`, `B` с обратными массами `imA`, `imB` и обратными моментами
`iiA`, `iiB` (у неподвижной стены обе равны `0`); единичная нормаль `n`,
направленная **от A к B**; глубина `d`; мировая точка контакта `p`.

```
1. Позиционная коррекция (пропорционально обратным массам):
   total = imA + imB;  если total === 0 → выход
   A.x -= n.x * d * imA / total;  A.y -= n.y * d * imA / total
   B.x += n.x * d * imB / total;  B.y += n.y * d * imB / total

2. Плечи:  rA = p − центр A,  rB = p − центр B

3. Скорости материальных точек контакта (2D, v + ω × r):
   vA = (A.vx − A.angvel*rA.y,  A.vy + A.angvel*rA.x)
   vB = (B.vx − B.angvel*rB.y,  B.vy + B.angvel*rB.x)
   vRel = vB − vA;   vn = vRel · n

4. Если vn >= 0 — точки уже расходятся, импульс не нужен (коррекция позиции
   из п.1 остаётся).

5. Нормальный импульс:
   rnA = rA.x*n.y − rA.y*n.x;   rnB = rB.x*n.y − rB.y*n.x
   effN = imA + imB + rnA²*iiA + rnB²*iiB
   jn = −(1 + restitution) * vn / effN
   A.v −= n*jn*imA;  A.angvel −= rnA*jn*iiA
   B.v += n*jn*imB;  B.angvel += rnB*jn*iiB

6. Трение по касательной t = (−n.y, n.x), зажатое кулоновским конусом:
   vt  = vRel · t
   rtA = rA.x*t.y − rA.y*t.x;   rtB = rB.x*t.y − rB.y*t.x
   effT = imA + imB + rtA²*iiA + rtB²*iiB
   jt = clamp(−vt / effT, −friction*jn, friction*jn)
   применяется так же, как jn, но вдоль t
```

### 4.6 Что такое `linvel()` у Rapier

`body.translation()` возвращает позицию **origin** тела, а `body.linvel()` —
скорость **центра масс**. У нашей динамики центр масс совпадает с
геометрическим центром бокса (коллайдер — единственный, смещён ровно на
полразмера), поэтому `linvel()` можно класть в скорость центра **без
пересчёта**, а вот позицию переводить через `boxCenterFromOrigin` — нужно.

⚠️ Это утверждение обязательно подтвердить пробным тестом (шаг 6.1.4). Если
окажется наоборот, вся реконсиляция будет систематически врать при вращении
ящика, а ошибка тихая — визуально похожа на «немного дрожит».

## 5. Принятые решения (не пересматривать)

| Решение | Обоснование |
|---|---|
| **Предсказываются только тела, связанные со своим танком** — прямой контакт плюс транзитивно соседи по контакту. Остальные идут по интерполяции, как сейчас. | Если рисовать на «сейчас» **все** тела, то ящик, который толкает *чужой* танк, будет опережать его спрайт на 100 мс: для наблюдателя танк толкает ящик «на расстоянии». Выборочность локализует артефакт туда, где его не видно. |
| **Скорости тел приходят по сети** — протокол v4, байт-флаг «движется» + `vx/vy/angvel` только для движущихся тел. | Оценка скорости конечной разностью между кадрами 30 Гц отстаёт на кадр и сильнее всего врёт в момент удара — ровно там, где предсказание должно быть точным. Покоящиеся ящики (их большинство) от флага не дорожают. |
| **Часы симуляции одни** — предсказанные ящики шагает `TankPredictor`, своего аккумулятора у `MapDynamics` нет. | Контакт танк↔ящик должен разрешаться в одном и том же шаге, иначе появится собственный рассинхрон внутри клиента. Плюс replay при реконсиляции автоматически переигрывает и ящики. |

## 6. Шаги реализации

### 6.1 Протокол v4 — скорости динамических тел

#### 6.1.1 Сервер отдаёт скорости

[src/server/parts/Map.js](../src/server/parts/Map.js), `getDynamicMapData()`:

Для каждого тела определить, покоится ли оно: `body.isSleeping()` **или**
модуль `linvel()` и `|angvel()|` ниже порога (константа модуля,
например `REST_VELOCITY_EPSILON = 0.01` — страховка на случай, если сон в
Rapier окажется выключен).

- покоится → `[x, y, angle]` (как сейчас);
- движется → `[x, y, angle, vx, vy, angvel]`.

Все числа через `roundTo2Decimals` ([src/lib/formatters.js](../src/lib/formatters.js)),
как уже сделано для позиции.

#### 6.1.2 Кодек

[src/lib/snapshotCodec.js](../src/lib/snapshotCodec.js), `writeDynamics` /
`readDynamics`. Новая раскладка одного тела:

```
uint8    index          // N из ключа dN
uint8    moving         // 0 | 1
float32  x
float32  y
float32  angle
float32  vx      \
float32  vy       > только если moving === 1
float32  angvel  /
```

`writeDynamics` ставит `moving = data.length > 3`. `readDynamics` читает хвост
только при флаге и возвращает массив той же длины (3 или 6) — так писатель и
читатель остаются зеркальными, а потребители различают режим по длине.

`BODY_BUFFER_SIZE = 65536` — запаса хватает с большим избытком (20 ящиков
`canopy` дают ~520 байт), менять не нужно.

#### 6.1.3 Версия формата

[src/config/opcodes.js](../src/config/opcodes.js): `SNAPSHOT_FORMAT_VERSION = 4`
плюс строка в комментарии рядом с описаниями v2/v3:

```
// v4: скорости динамики карты (блок dynamics: флаг moving + vx/vy/angvel)
```

`unpackFrame` уже отбрасывает кадр с несовпадающей версией с предупреждением в
консоль — отдельная миграция не нужна, достаточно перезагрузить страницу.

### 6.2 Новый модуль `src/lib/rigidBody.js`

Чистые функции, без Pixi/Rapier/DOM. Формат тела:

```js
{ x, y, angle, vx, vy, angvel, invMass, invInertia, linearDamping, angularDamping }
```

Стена/статика — `invMass: 0, invInertia: 0`.

Экспорты:

- **`integrate(body, dt)`** — один шаг интеграции. Порядок обязан совпадать с
  `TankPredictor._step` (см. 3.3): позиция интегрируется скоростью **до**
  демпфирования, затем `v *= 1/(1 + dt·damping)`. Угол нормализуется
  `normalizeAngle` из [src/lib/math.js](../src/lib/math.js).
- **`resolveContact(a, b, contact, { restitution, friction })`** — реализация
  формул 4.5. `contact` — `{ nx, ny, depth, cx, cy }` в формате, который отдаёт
  `obbVsObb`. Мутирует оба тела.

### 6.3 `src/lib/collision.js` — контакты со стенами списком

`obbVsTileGrid` отдаёт **суммарное выталкивание**, но не нормаль — для
импульсного решателя этого мало. Заменить его на:

**`collectTileContacts(obb, { map, solidTiles, tileSize })`** → массив
`{ nx, ny, depth, cx, cy }` по всем задетым сплошным клеткам.

Внутри — тот же отбор кандидатных клеток по консервативному AABB, что и сейчас
в `obbVsTileGrid` (строки с `extentX`/`extentY`), но без внутренних итераций:
многократный проход теперь делает решатель (`SOLVER_ITERATIONS`), и внутренний
угол из двух тайлов разрешается им естественно.

`obbVsTileGrid` удалить вместе с его тестами (после замены он не используется
никем). `obbVsObb`, `boxCenterFromOrigin`, `CONTACT_MANIFOLD_RATIO` остаются
без изменений.

### 6.4 `src/client/MapDynamics.js` — из реестра геометрии в предиктор

Класс остаётся единственным источником геометрии динамики (его API читают
`ShotPredictor` и `ShotEffectController` — их менять не нужно), но получает
состояние, режимы и симуляцию.

#### 6.4.1 Состояние тела

```js
{
  // геометрия
  halfW, halfH,
  // динамика
  x, y, angle, vx, vy, angvel,        // x/y — ЦЕНТР бокса
  invMass, invInertia, linearDamping, angularDamping,
  // режим
  mode,                                // 'follow' | 'predicted'
  error: { x, y, angle },              // сглаживание расхождения с сервером
  lastContactTime,                     // мс, performance.now()
  lastServer: { x, y, angle, vx, vy, angvel },  // последний авторитетный кадр
}
```

#### 6.4.2 Константы модуля (по образцу `TankPredictor`)

| Константа | Значение | Смысл |
|---|---|---|
| `CAPTURE_MARGIN` | 2 юнита | насколько раздуть OBB танка при проверке захвата тела в предсказание |
| `PREDICTION_HOLD_MS` | 300 | сколько держать тело предсказанным после последнего контакта |
| `MAX_PREDICTED_BODIES` | 12 | потолок множества (стена `canopy` — 20 ящиков, транзитивный захват может втянуть всю) |
| `ERROR_DECAY_RATE` | 10 | доля затухания ошибки в секунду (как у танка) |
| `ERROR_SNAP_DISTANCE` | 24 | порог снапа расхождения, юниты |
| `DEMOTE_POSITION_EPSILON` | 1 юнит | насколько предсказание должно сойтись с интерполяцией, чтобы вернуть тело в `follow` |
| `DEMOTE_ANGLE_EPSILON` | 0.02 рад | то же по углу |

#### 6.4.3 Методы

- **`setMap({ physicsDynamic, scale, setId })`** — как сейчас (полуразмеры,
  центр через `boxCenterFromOrigin`), плюс масс-инерционные свойства по
  формулам 4.3 и запоминание `setId` (он нужен `getRenderData`, чтобы
  выдать блок под правильным ключом — см. 3.1). Все тела стартуют в `follow`.

- **`update(game)`** — как сейчас, но обновляет трансформы **только тел в
  режиме `follow`**. Предсказанные тела своим состоянием владеют сами.

- **`beginReconcile(snapshot)`** — принять авторитетный кадр. Для каждого тела
  из блока `setId`: запомнить `lastServer` (позиция → центр; скорость как есть,
  см. 4.6; при коротком массиве из 3 чисел скорости нулевые). Для тел в режиме
  `predicted`: сохранить копию текущего предсказанного состояния и **заменить
  состояние авторитетным**.

- **`finishReconcile()`** — после replay (см. 6.5.2): для каждого предсказанного
  тела прибавить к `error` разницу «сохранённое предсказание − новое
  состояние»; если `hypot(error.x, error.y) > ERROR_SNAP_DISTANCE` — обнулить
  `error` (снап вместо протаскивания).

- **`integratePredicted(dt)`** — `integrate(body, dt)` из `rigidBody.js` для
  каждого предсказанного тела.

- **`getPredictedBodies()`** — массив живых (мутируемых) тел для решателя.

- **`capture(tankObb, localNow)`** — перевод тел в `predicted`:
  1. раздуть `tankObb` на `CAPTURE_MARGIN` и проверить `obbVsObb` против всех
     тел; пересёкшиеся — в `predicted`, `lastContactTime = localNow`;
  2. **транзитивное замыкание**: повторять проход, добавляя тела, пересекающие
     (с тем же запасом) уже предсказанные, пока множество растёт или пока не
     упрётся в `MAX_PREDICTED_BODIES`;
  3. при переводе тела в `predicted` засеять его состояние из `lastServer`
     (позиция + скорость), `error = {0,0,0}`.

- **`demoteIdle(localNow)`** — вернуть в `follow` тела, у которых
  `localNow − lastContactTime > PREDICTION_HOLD_MS` **и** предсказанный
  трансформ сошёлся с интерполированным в пределах `DEMOTE_POSITION_EPSILON` /
  `DEMOTE_ANGLE_EPSILON`. Остаток расхождения уходит в `error` и затухает —
  скачка быть не должно. Тело, которое не сошлось, продолжает держаться
  предсказанным.

- **`decayError(elapsed)`** — экспоненциальное затухание `error` у всех
  предсказанных тел, множитель `max(0, 1 − elapsed/1000 · ERROR_DECAY_RATE)`
  (в точности как `_visualError` в `TankPredictor.update`).

- **`getBoxes()` / `getBox(key)` / `toLocal(key, x, y)`** — сигнатуры не
  меняются, но отдают **рендерные** боксы: для `predicted` — состояние плюс
  `error`, для `follow` — интерполированное. Так трассер `ShotPredictor` и
  осколки `ShotEffectController` попадают ровно туда, где ящик нарисован.
  Решатель работает с состоянием напрямую, без `error`.

- **`getRenderData()`** → `{ [setId]: { dN: [x, y, angle] } }` **только для
  предсказанных тел**, в соглашении «угол объекта» (обратный перевод из 4.1),
  в мировых (масштабированных) координатах — ровно то, что ждёт
  `parts/Map.js update()`. Если предсказанных тел нет — вернуть `null`.

⚠️ Метод сброса по-прежнему **не добавлять** (см. 3.4).

### 6.5 `src/client/TankPredictor.js` — контакт и оркестрация

#### 6.5.1 Конструктор и карта

- конструктор принимает необязательный `mapDynamics` (как было до отката:
  `new TankPredictor({ ...data.prediction, mapDynamics })`);
- вернуть метод `setMap({ map, step, scale, physicsStatic })`, строящий
  `this._grid = { map, solidTiles: physicsStatic || [], tileSize: step * scale }`.

⚠️ **Инвариант**: без вызова `setMap()` и без `mapDynamics` проход
столкновений — полный no-op, а реплика движения остаётся бит-в-бит прежней.
`tests/server/TankPredictorParity.test.js` строит предиктор именно так и обязан
остаться зелёным **без правок**.

#### 6.5.2 Шаг симуляции

В конце `_step(keys)`, после интеграции и демпфирования танка, вызвать
`this._resolveWorld(dt)`:

```
_resolveWorld(dt):
  если нет ни _grid, ни _mapDynamics → выход

  tank = тело танка в формате rigidBody.js
         { x, y, angle, vx, vy, angvel из state;
           invMass = 1/9600, invInertia = 1/80000 (формулы 4.3);
           halfW = m.size*2, halfH = m.size*1.5 }

  mapDynamics?.capture(tank, localNow)     // захват тел в предсказание
  mapDynamics?.integratePredicted(dt)      // интеграция ящиков
  bodies = mapDynamics?.getPredictedBodies() ?? []

  contacts = []
  для tank:            collectTileContacts → contacts (партнёр — статика)
  для каждого ящика:   collectTileContacts → contacts (партнёр — статика)
  для каждой пары ящиков:      obbVsObb → contacts
  для пары (tank, ящик):       obbVsObb → contacts

  повторить SOLVER_ITERATIONS (4) раз:
    для каждого контакта → resolveContact(a, b, contact, параметры 4.4)

  записать состояние tank обратно в this._state
  mapDynamics?.noteContacts(...)   // отметить контактировавшие тела
  mapDynamics?.demoteIdle(localNow)
```

Контакты собираются **один раз** за шаг, а решатель проходит по ним
`SOLVER_ITERATIONS` раз — это стандартный sequential impulse и он же заменяет
внутренние итерации удалённого `obbVsTileGrid`.

Статический партнёр — общий замороженный объект
`{ invMass: 0, invInertia: 0, ... }` с координатами центра задетого тайла
(нужны для плеча `rB`, хотя при нулевых обратных массах вклад и так нулевой).

#### 6.5.3 Что НЕ делать

- **Не** возвращать приведение серверного состояния к геометрии в
  `onServerState` — рассинхрона времён больше нет, а тот код давал пилу 30 Гц.
- **Не** возвращать зажим позиции рендера в `getRenderState()` против динамики.
  Танк и ящик теперь из одной симуляции. `getRenderState()` остаётся
  тривиальным (`state + visualError`).
- **Не** трогать `ERROR_SNAP_DISTANCE = 100` без отдельного замера: значение
  относится к предсказанию танка, а не к динамике.

#### 6.5.4 Затухание ошибки ящиков

В `update(localNow)`, рядом с затуханием `_visualError`, добавить
`this._mapDynamics?.decayError(elapsed)`. Так у всей предсказанной подсистемы
одни часы (решение из раздела 5).

### 6.6 `src/client/main.js` — проводка

1. **Конструктор** (обработчик `PS_CONFIG_DATA`): вернуть передачу
   `mapDynamics` в `TankPredictor`:
   ```js
   predictor = new TankPredictor({ ...data.prediction, mapDynamics });
   ```
2. **`MAP_DATA`** (`socketMethods[PS_MAP_DATA]`): вернуть `predictor?.setMap(data)`
   рядом с существующим `mapDynamics?.setMap(data)`.
3. **`ws.onmessage`** — реконсиляция скобкой вокруг replay, порядок критичен:
   ```js
   mapDynamics?.beginReconcile(frame.snapshot);   // авторитетное состояние ящиков
   predictor.onServerState(frame.player, frame.serverTime, interpolator.offset, now);
   mapDynamics?.finishReconcile();                // расхождение → error ящиков
   ```
   `predictor.onServerState` внутри переигрывает историю ввода, а каждый его
   `_step` двигает и ящики — поэтому `finishReconcile` обязан быть **после**.
4. **`renderTick`** — наложить предсказанные ящики поверх интерполяции, тем же
   приёмом, что и свой танк:
   ```js
   const dynamicsRender = mapDynamics?.getRenderData();

   if (dynamicsRender) {
     applyGameData(dynamicsRender);
   }
   ```
   Место — после `applyGameData(game)` и до/после блока своего танка (порядок
   между ними безразличен, ключи не пересекаются).
5. `mapDynamics?.update(...)` в `renderTick` и отсутствие сброса по `PS_CLEAR`
   — **оставить как есть**, включая комментарий про `CLEAR`.

## 10. Риски

- **Расхождение решателей.** Клиентский решатель — приближение Rapier, а не его
  копия. Реконсиляция прячет остаток, но при одновременном толчке нескольких
  ящиков возможен заметный снап. Рычаги: `SOLVER_ITERATIONS`,
  `ERROR_SNAP_DISTANCE`. Мерить стендом, а не на глаз.
- **Стоимость кадра.** Транзитивный захват в стене из 20 ящиков может втянуть
  всю стену; `MAX_PREDICTED_BODIES` — обязательный предохранитель.
- **Семантика `linvel()`** (4.6) — если пробный тест 6.1.4 её не подтвердит,
  переписать перевод скорости, прежде чем идти дальше. Ошибка тихая.
